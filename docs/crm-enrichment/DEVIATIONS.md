# Deviations from the design

Where the build departs from `design-reference/sentral/`, and why. A deviation is a decision, not a
shortcut: each names the constraint.

| ID | Where | Design | Built | Reason |
|---|---|---|---|---|
| V-01 | Every screen | Buttons that navigate (`go(route)`) | Links with the same classes | Control substitution: the prototype has no router |
| V-02 | Shell, rail footer | «EU residency · Stockholm» | «EU residency · Frankfurt» | D-35: the real region is eu-central-1 |
| V-03 | Shell, nav badges (Tickets 7, Feed 9, Inbox 4) | Fixed numbers | Real counts when the source exists; nothing at zero | Never fabricate |
| V-04 | Shell, notifications footer | «In app · email · desktop · push» | «In app» | Only in-app notifications exist; the other channels arrive with their providers |
| V-05 | Shell, assistant | A conversation with canned answers | The unconnected state, prompts and input disabled | Phase 7 (AI gateway, a Claude key) |
| V-06 | Shell, product picker | Product state dots (operational/degraded) | Connected or not | Product health is measured in phase 8 |
| V-07 | Overview KPIs | Five cards always | Cards whose source exists (tickets and pipeline arrive with phase 1) | Never fabricate |
| V-08 | Overview, applications | p95, error rate, version | «—» | No source until phase 8 measures command latency and errors |
| V-09 | Overview, trials | «First survey: Sent 97 d ago / Not sent» | «—» | Needs Orgpuls' count-only survey events (D-21) |
| V-10 | Overview, headline | Fixed sentence | A sentence built from the facts that exist | Never fabricate |
| V-11 | Overview, delta on paying organizations | +6 | The change in paid subscriptions since the snapshot 30 days ago | The daily snapshot counts per product |
| V-12 | Settings › Visibility defaults | Deals and leads «Owner's group and sub-groups» | Everyone for every type | D-16: rules default to unrestricted |
| V-13 | Login, second factor, no access | Not in the design | Built in the design's language | D-41 |
| V-14 | Response headers | — | Referrer-Policy same-origin (was no-referrer) | A form posted before hydration must carry its Origin or the server action refuses it |
| V-15 | Shell header at 390 px | Gap 14 px between header controls | Gap 10 px below 768 px | The design's header overflows a 390 px screen by 2 px; the gap is the only slack |
| V-16 | Notifications from mail and workflows | — | Kind «system» (the tabs are the design's: mentions, reminders, security) | The design's notification tabs are fixed; mail and workflow notices sit under All |
| V-17 | Inbox thread status | Waiting on you / New / Replied / Waiting on contact, rule unspecified | New: nothing sent; Waiting on you: the contact wrote last; Replied: they started and we wrote last; Waiting on contact: we started and wrote last | The design names the states without a rule |

| V-23 | Credits top-up (Feed › Enrichment) | «Buy top-up →» | Left out; usage counted from the ledger | D-17: nothing is sold |
| V-24 | Automation › Templates | «Trial nurture» on day 7 of a 30-day trial | Triggered by org.created with a two-business-day delay | Orgpuls sends no trial-day event; the trial length is 15 days |

## Session reports (R-SECURITY-04: `supabase/functions/session-report`, `lib/supabase/report.ts`, 0047–0048)

The sign-in, the second factor and the middleware now report to the session register through the `session-report`
edge function. The function holds the service role, so the app still holds none. The app sends the person's own
token, and the function takes the session from that token's claim and the address from the account, never from the
body. Signing out ends the row as «signed out» (0048 `session_sign_out`, called with the person's JWT).

## Storage (0052: `supabase/functions/storage-sign`, `lib/storage/*`; R-PROJECTS-01, R-MOBILE-04, R-MEETINGS-06, R-SECURITY-03)

Three private buckets (`record-files`, `meeting-files`, `privacy-exports`), each limited to the size and types its RPC
accepts, with no storage policy. The `storage-sign` edge function holds the service role: it checks the caller's own aal2
token with Auth, asks `worker_storage_check` (service role only) whether this staff member, in this session, may upload to
or download from this exact path now, and only then signs. The app's server takes the path from the RPC that checked the
rights, never from the browser. Proved by `supabase/tests/storage_invariants.sql`, `tests/storage-sign.test.ts`,
`scripts/dev/storage-sign-e2e.mjs` and `scripts/dev/storage-browser.mjs` (local stack).

| ID | Where | Spec / contract | Built | Why |

| V-STORAGE-01 | «Signer connected» | An `integration_connections` row or a field | The function's own `status` mode (are its three private buckets there?), asked by the server with the staff member's token and remembered for a minute (a failure for fifteen seconds). ## Jobs (0054: `supabase/functions/jobs-run`, `supabase/functions/_shared/{transcript,zip,privacy-package}.ts`, `lib/jobs/*`; R-MEETINGS-06, R-SECURITY-03)

Two jobs that need no outside provider run now: the transcript upload reader and the privacy access package. There is no
cron and no new secret: the app's server calls `jobs-run` with the person's own aal2 token right after the action that made
the job runnable (`meeting_transcript_upload_done`; `privacy_export`), and again on «Read now» / «Write package now». The
function checks the token with Auth, then asks `worker_jobs_claim` (service role only) whether this caller may run this job
(their own landed upload; an export they asked for or approved, with global:security) and claims it for five minutes, so a job
already running or finished is not run twice. Proved by `supabase/tests/storage_invariants.sql` (0054 block),
`tests/transcript.test.ts`, `tests/jobs-run.test.ts` and `scripts/dev/jobs-e2e.mjs` (local stack, API and browser).

| ID | Where | Spec / contract | Built | Why |
|---|---|---|---|---|
| V-JOBS-01 | How a job starts | A queue worker reads `pgmq` `jobs` (`meeting_upload_parse`, `privacy_package`) | The server calls `jobs-run` after the action, with the person's JWT; the queue messages are still sent and nothing reads them (a later queue worker would find the job finished: the worker functions refuse a second run) | No cron and no new secret: the person's own session is the authority, and the database decides what it may run |
| V-JOBS-02 | A job whose call failed | Retried by the worker | It waits («Waiting to be read …» with «Read now»; «waiting to be written» with «Write package now» for the requester). Any later call of the same kind also takes along up to three such jobs that landed two minutes ago or more. A job claimed three times without finishing fails with `too_many_attempts` | There is no scheduler; the claim's five minutes let a crashed run be taken over, and the attempt limit keeps a file that crashes the reader from looping |
| V-JOBS-03 | The reader's result | «handed to `worker_transcript_ready`» | `worker_upload_parsed` (0042) for segments, and the new `worker_upload_failed(upload, reason)` for a reason code (`empty`, `too_large`, `not_text`, `docx_invalid`, `no_segments`, `too_many_segments`, `missing`, `rejected`, `too_many_attempts`); the transcript names the reason in words | `worker_transcript_ready` is the provider's path and refuses an upload's transcript; `worker_upload_parsed(null)` could only say `parse_failed` |
| V-JOBS-04 | Untimed transcripts | Segments with start and end | A .txt or .docx without timings is stored at start 0 with no end, and the transcript shows no clock for it (no «00:00» on every line, no duration) | The schema requires a start; showing invented times would fabricate them |
| V-JOBS-05 | The original file | «Deleted once read» (by the files purge worker) | `jobs-run` deletes it right after the database took the result (read or failed); the `files_purge` message `worker_upload_parsed` queues stays as the fallback | No purge worker runs; the dialog promises deletion |
| V-JOBS-06 | The access package | «JSON (plus CSV)» | `privacy/<job>/access-package.zip`: `about.json` (job, time, rows per section) and one pretty-printed JSON file per section of `worker_privacy_package`; no CSV. Over 50 MB the job fails with `package_too_large` | One file per module is readable by the person; CSV of nested rows would lose fields |
| V-JOBS-07 | Reading .docx | npm:fflate (or similar) | A small ZIP reader and writer on `DecompressionStream`/`CompressionStream` (`_shared/zip.ts`): stored or deflated entries, CRC checked, inflating stops at the limit; no ZIP64 or encryption (`docx_invalid`) | The same module runs in Deno and in vitest without a dependency or an import map; a 5 MB .docx never needs ZIP64 |
| V-JOBS-08 | Speakers in plain text | — | «Name: text», «[Name] text», «Name  0:03» headers (two spaces or a tab) and Teams' «timing / Name / text» are read as speakers; a line such as «Note: …» is read as speaker «Note» | A plain line has no markup; the owner sees the labels in Speakers and can leave them unmapped |
| V-JOBS-09 | Erasure | — | `privacy_approve` erases in the database in the same call; nothing is run after it | An erasure writes no package |
| V-JOBS-10 | Hosted | — | `jobs-run` is not deployed by this change: hosted, the call answers «not connected», and the screens say the job waits | Deploying is a separate step (`npm run functions:deploy`) |
